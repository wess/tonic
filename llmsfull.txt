# Tonic

> Tonic compiles Elixir and supported Erlang source through LLVM into standalone
> native executables. Its goal is 100% Elixir compatibility across BEAM and LLVM.

Tonic is currently a beta. Full compatibility is a goal, not a statement about
the current release. Read the compatibility report before recommending an API,
package, or deployment workflow. A successful package test covers the tested
scenario, not every API in that package.

This index follows 0.1.1-beta.1 development source, including unreleased changes after
0.1.0-beta.3. Use the documentation from the matching tag for installed release
bundles; new native test/release and networking behavior requires the checkout.

The reference baseline is Elixir 1.18.3 / Erlang OTP 27; CI pins OTP 27.2.4.
Upstream documentation and source should match that baseline. Newer Elixir or
OTP behavior requires separate verification. Native compilation preserves the
language's semantics while using a different runtime and compilation artifact.
BEAM bytecode loading, distributed nodes, hot code replacement, and arbitrary
NIF compatibility are not provided by the current release.

For application code, prefer ordinary Elixir and existing Mix/Hex workflows.
For compiler work, reproduce a difference on both engines and add a regression
before changing semantics. Never treat an implementation gap as a new language
rule or change a reference fixture to accept incorrect native behavior.

# Elixir semantics and the Tonic compiler

Write idiomatic Elixir that behaves the same on the BEAM and Tonic's LLVM
backend. Tonic's goal is 100% Elixir compatibility. The current beta implements
a subset; [known differences](https://github.com/wess/tonic/blob/main/docs/compatibility.md) describe gaps to close, not a
separate language specification.

This guide covers application code and compiler contributions. Use the
[reference](https://github.com/wess/tonic/blob/main/README.md) for CLI and Mix details, and the
[roadmap](https://github.com/wess/tonic/blob/main/TODO.md) for work still ahead.

## Establish the reference version

The test baseline is Elixir 1.18.3 / OTP 27. CI installs OTP 27.2.4. Some bundled
Erlang library sources come from OTP 27.3; their provenance is recorded in
[notice](https://github.com/wess/tonic/blob/main/notice) and [licenses](https://github.com/wess/tonic/blob/main/licenses/). Record the exact versions
when investigating behavior that differs between OTP patch releases.

Use versioned upstream references:

- [Elixir 1.18.3 documentation](https://hexdocs.pm/elixir/1.18.3/)
- [Elixir 1.18.3 source and tests](https://github.com/elixir-lang/elixir/tree/v1.18.3)
- [Erlang/OTP 27 documentation](https://www.erlang.org/docs/27/)
- [Erlang/OTP 27.2.4 source and tests](https://github.com/erlang/otp/tree/OTP-27.2.4)

Upstream documentation defines documented behavior; pinned source and small
reference programs resolve edge cases. Tonic's tests establish the behavior
actually exercised. An exported function or an accepted option alone does not
establish correct implementation. Consult the compatibility report for partial
implementations, unsupported options, and backend limits.

## Preserve Elixir semantics

- Values are immutable. Rebinding a variable gives it a new value; it does not
  mutate an earlier value. `=` matches patterns, and `^value` matches against an
  existing binding. Clause order, guards, and variable scope affect behavior.
- Only `false` and `nil` are falsy. `and`, `or`, and `not` require a boolean
  left operand or argument; `&&`, `||`, and `!` accept truthy values. Preserve
  short-circuiting and the returned operand.
- `==` permits numeric equality between integers and floats; `===` distinguishes
  their types. Integer arithmetic must retain arbitrary precision. Map keys use
  exact equality; `1` and `1.0` can be distinct keys. Do not turn Elixir term
  ordering into host-language ordering.
- Strings are UTF-8 binaries; charlists are lists of code points. Byte counts,
  code-point counts, and grapheme counts differ. Binary pattern sizes and
  bitstring segment sizes must follow Elixir's rules.
- Lists are linked lists, and improper lists are possible. Tuples, lists, maps,
  structs, and keyword lists are distinct. Keyword lists preserve ordering and
  duplicate keys; structs retain their module identity.
- Guards have restricted operations and special failure behavior. An operation
  that fails in a guard does not behave like the same operation in a function
  body. Match upstream acceptance and rejection as well as successful results.
- Preserve left-to-right effects, pattern failure, exception class and reason,
  `try`/`rescue`/`catch`/`else`/`after`, and tail-call behavior. A program producing
  the expected final number can still have incorrect observable behavior.
- Do not depend on map enumeration order, numeric pid/reference identities, or
  scheduling between independent senders. Test the documented guarantees, and
  isolate representation-dependent output when comparing engines.

For ordinary application code, use pattern matching, small functions, explicit
data, and standard protocols. Add a process when state ownership, concurrency,
or failure isolation calls for one; a module does not need a process merely to
organize functions. Avoid converting untrusted strings into new atoms.

## Understand macros and compilation phases

`alias` changes name resolution, `import` brings functions or macros into local
scope, `require` enables a module's macros, and `use` invokes its `__using__/1`
macro. These have different effects. Resolve local, imported, and remote calls
with the correct arity and visibility.

`quote` constructs AST and `unquote` inserts a value into it. Preserve variable
hygiene, AST metadata, caller environments, aliases, and `unquote_splicing`.
Module attributes are evaluated in their compilation context; they are not
runtime global variables. Generated definitions, `defoverridable`, `super`,
protocols, and compilation callbacks must retain their phase and ordering.

Tonic parses and expands source in its own compiler. Computed macros execute
through the native macro host and bundled evaluator. Mix evaluates project
metadata and compile configuration for project builds. Distinguish those two
paths when diagnosing compile-time behavior.

The current `@after_compile` callback receives LLVM IR rather than a BEAM module
binary; interpreted modules receive an empty binary. `tonic check` parses and
expands without LLVM generation or after-compilation callbacks. See the
[callback and macro limitations](https://github.com/wess/tonic/blob/main/docs/compatibility.md#macros-and-compilation-callbacks)
before assuming artifact-dependent tooling is portable.

## Understand BEAM and OTP behavior

A BEAM process is a lightweight runtime process with its own state and mailbox,
not an operating-system process. Tonic implements Elixir processes as stackful
coroutines driven by tokio tasks, with per-process heaps and copied messages.
The implementation differs; the observable process contract is the target.

`send/2` is asynchronous. Selective `receive` scans for matching messages while
retaining unmatched messages. Signals from one sender to one destination have
ordering guarantees; independent senders do not establish a global order.
Test synchronization with messages and monitors rather than arbitrary sleeps.
The [OTP 27 process reference](https://www.erlang.org/docs/27/system/ref_man_processes.html)
describes the signal and mailbox model.

Links propagate exit signals; monitors report termination with `:DOWN` messages.
Trapping exits changes how eligible exit signals are handled, while `:kill` is
untrappable. A GenServer call is a request/reply protocol that can time out or
exit; a cast does not acknowledge successful processing. Preserve these
distinctions and test races explicitly.

Use supervisors for restart policy and lifecycle ownership. Choose restart
strategies and child specifications according to the dependency between child
processes. A supervisor cannot make an unsafe external side effect reversible.
Keep application startup and runtime configuration in the appropriate phase.
See [GenServer](https://hexdocs.pm/elixir/1.18.3/GenServer.html) and
[Supervisor](https://hexdocs.pm/elixir/1.18.3/Supervisor.html).

BEAM features such as distributed nodes, dynamic bytecode loading, hot code
replacement, dirty NIF schedulers, and introspection require dedicated native
implementations or interoperability work. They are current compatibility gaps.
Do not claim that native executables load `.beam` files, or that compiling an
Erlang module establishes distributed-node interoperability.

## Keep Mix and Hex workflows ordinary

Use `mix.exs`, `mix.lock`, configuration files, and `mix deps.get` as usual.
Tonic compiles fetched dependency sources; it does not link their BEAM files.
Fetching a package establishes availability, not native compatibility. Keep the
lockfile and package version when reporting a failure.

```sh
mix deps.get
tonic check .
tonic build . -o program
./program
```

With Tonic's Mix archive installed, `mix tonic check`, `mix tonic build`, and
`mix tonic run` invoke the native compiler. Ordinary `mix compile`, `mix run`,
and `mix release` use the project's configured Mix pipeline. Opting into the
`:tonic` compiler produces a native artifact; it does not produce BEAM modules
for `mix run` or `mix release`. The development `Tonic.native/1` project adapter
routes ordinary run/test/release tasks to native equivalents. `tonic test` and
`mix tonic test` run ExUnit natively, and `mix tonic release` bundles the native
executable with relocatable application assets and runtime configuration.

Current project boundaries, supported dependency compilers, NIF restrictions,
and application startup behavior are in the
[compatibility report](https://github.com/wess/tonic/blob/main/docs/compatibility.md#supported-project-boundaries).

## Find the implementation

| Mix projects and NIF builds | `compiler/src/project.rs`, `project.exs`, `nif.rs` |

Compiled code and runtime code share a term ABI and process context. Heap values
live across calls through shadow-stack slots; native BIFs must root live terms
across allocations and reload values after moving collection. Retaining a raw
heap pointer across allocation can become a use-after-move bug.

The code generator uses LLVM `tailcc` calls for tail positions. Exceptions use
pending state in the process context and a zero return sentinel. Changes to
calling conventions, context offsets, term tags, or root layout must agree
across compiler and runtime. Read the source before changing an ABI detail.

## Reproduce and close a compatibility gap

1. Reduce the issue to a small `.exs` program or locked Mix project. Record the
   Tonic commit, OS, architecture, Elixir/OTP versions, and compiler settings.
2. Run the same input under reference Elixir and Tonic. Capture exit status,
   stdout, stderr, exceptions, and relevant effects. Identify whether failure
   occurs in parsing, expansion, macro execution, LLVM generation, linking,
   runtime behavior, or project loading.
3. Check the pinned upstream documentation and source. Separate documented
   language semantics from an incidental runtime representation or race.
4. Add a focused regression to `tests/cases/` or `compiler/tests/`, then fix the
   responsible layer. Successful execution fixtures need a reference `.out`.
   Use Rust integration tests for compile failures, diagnostics, exit status,
   and behavior the stdout fixture runner does not assert.
5. Run the focused checks on both engines. Exercise affected GC/process paths
   under stress. Update the compatibility report and roadmap when support
   changes; keep any remaining limitations explicit.

Build before running native comparisons:

```sh
cargo build --workspace --locked
cargo test --workspace --locked
cargo build --release --workspace --locked
bash tools/compare.sh tests/cases/basics.exs
bash tests/run.sh tests/cases/basics.exs
TONIC_GC_STRESS=1 TONIC_GC_VERIFY=1 bash tests/run.sh tests/cases/basics.exs
```

For a new successful fixture, `bash tests/run.sh --bless tests/cases/example.exs`
records output from reference Elixir. Review that output, then run both fixture
and live-reference checks. Never bless native output as the reference.

The runners require successful exits and compare stdout, normalizing only
ExUnit's elapsed-time summary. They retain stderr for failure diagnostics;
they do not assert matching stderr or all external effects. Concurrent tests
need assertions for protocol behavior, process exits, and cleanup.

The [CI workflow](https://github.com/wess/tonic/blob/main/.github/workflows/ci.yml) is the authoritative list of
release checks. It includes Linux/macOS builds, Rust tests, Mix archive tests,
locked Hex comparisons, native HTTP checks, fixtures, live Elixir parity, GC
stress, installation verification, and a supervision soak. Passing these
checks supports their covered scenarios; it does not establish full parity.

# tonic

**0.1.1-beta.1 · development beta.** Start with scripts and small native applications.
Visit the [Tonic website](https://wess.io/tonic/).
Install with `brew install wess/packages/tonic` or
`curl -fsSL https://wess.io/tonic/install.sh | sh`; the
[release guide](https://github.com/wess/tonic/blob/main/docs/release.md) covers the Debian package, bundles and Mix
tasks. See the
[compatibility report](https://github.com/wess/tonic/blob/main/docs/compatibility.md) for tested packages and limitations.
Remaining work is tracked in [TODO.md](https://github.com/wess/tonic/blob/main/TODO.md).

The 0.1.1-beta.1 source checkout includes unreleased portability changes after
0.1.0-beta.3: native test/release workflows, umbrella builds, an API conformance
inventory, Req support, resource reclamation and expanded networking. Build
from source for those changes; published beta.3 bundles retain their original
feature set.

An ahead-of-time compiler for **Elixir** that produces native executables via
**LLVM**, with a precise, moving garbage collector and an Erlang-style process
runtime built on **tokio**.

```
$ cat hello.exs
defmodule Greeter do
  def greet(name), do: "Hello, #{name}!"
end

IO.puts(Greeter.greet("world"))

$ tonic run hello.exs
Hello, world!

$ tonic build hello.exs -o hello && ./hello
Hello, world!
```

The goal is to be *as close to Elixir as possible*: same syntax, same
semantics, same standard library behaviour — down to `IO.inspect` pretty
printing, float formatting and exception messages. The test suite diffs tonic's
output against the reference Elixir implementation.

## Building

Requirements: Rust (1.88+) and clang/LLVM (18+) on your `PATH`.

```
cargo build --release
./target/release/tonic run examples/hello.exs
```

`target/release/tonic` finds its runtime (`libtonic_rt.a`) next to itself.
Override with `TONIC_RUNTIME=/path/to/libtonic_rt.a` and the compiler/linker
with `TONIC_CC=clang-18`.

Release bundles include the compiler, runtime library, and Mix archive. Build
and verify a bundle with Python 3.12+, installed Mix, and the Rust/LLVM toolchain:

```sh
python3 tools/release.py
python3 tests/release.py dist/*.tar.gz
```

## Usage

```
tonic run <file.exs>... [-- args]    compile (-O0 by default) and run
tonic build <file.ex>... [-o out]    compile to an executable (-O2 by default)
tonic emit-llvm <file.ex>... [-o x.ll]
tonic check <file.ex>...             parse + expand only
tonic test [project] [test paths]    compile and execute ExUnit natively
tonic inventory                     emit declared exports as JSON
```

Multiple files are compiled together as one program; top-level expressions in
the files run in order, like `elixir script.exs`.

### Mix and Hex

Tonic uses installed Mix to evaluate `mix.exs` and resolve the fetched dependency
graph. Keep using the usual `mix.exs`, `mix.lock`, and `deps/` conventions:

```sh
mix deps.get
mix deps.update decimal
mix hex.outdated
tonic build . -o program
tonic run . -- argument
```

Mix and Hex handle package resolution, fetching, checksums, and locks. Tonic
compiles dependency sources together with your application's sources. It never
links BEAM files into the executable. Unfetched, conflicting, or stale locked
dependencies fail with a diagnostic; Tonic does not silently skip them or fetch
packages during compilation. Hex, Git, and path dependencies use Mix's resolved
graph, including transitive dependencies, `only`, `targets`, and overrides.

Elixir/OTP and Mix are required on the development machine for project loading.
Set `TONIC_MIX` to select the Mix executable. Standalone `.ex` / `.exs` compilation
and the resulting native executable do not require Mix or BEAM.

Computed project metadata and configured `elixirc_paths` / `erlc_paths` are
supported. Compile-time configuration is evaluated by Mix's `Config.Reader`,
including imports and environment/target selection. Its values are embedded in
the executable. `config/runtime.exs` executes in the native program before
applications start, so runtime environment lookups remain runtime lookups.
Application specifications, startup modules, and runtime dependency edges are
preserved. A dependency with `runtime: false` is compiled but is not automatically
started. An escript `main_module` receives command-line arguments; an application
with a startup module and no escript entry keeps running.

### Mix tasks

Every command works through Mix as well as directly. The release bundle's
`install.sh` installs the Mix archive when Mix is present. From a checkout,
build and install it yourself:

```sh
cd mix
mix archive.build -o tonic.ez
mix archive.install ./tonic.ez
```

With `tonic` on `PATH`, use these in your application directory:

```sh
mix deps.get
mix tonic check
mix tonic build
mix tonic run -- one two
mix tonic build --deps-get -o ./program
mix tonic            # list the commands
```

`mix tonic.build`, `mix tonic.run` and `mix tonic.check` are the same commands.
`mix tonic build` defaults to `_build/<env>/tonic/<app>`. Set `TONIC` to the native
compiler executable or configure `tonic: [executable: "/path/to/tonic"]` in
`project/0`. Ordinary Mix dependency, Hex publishing, and package-management
tasks continue to use Mix.

### Native tests and releases

The development checkout supports ExUnit and relocatable native bundles:

```sh
tonic test
tonic test test/example_test.exs:12 --seed 0 --trace
mix tonic test --only integration --timeout 30000
mix tonic release -o ./native
./native/bin/my_app argument
```

Tests use the project's test paths/helpers and start applications before the
suite. File/directory/file:line selection, include/exclude/only tags, seed,
timeout, trace and failure-limit options are passed through the native runner.
Unsupported switches produce diagnostics. Releases include application `priv`
assets and evaluate runtime configuration when started, so the bundle can move
to a machine without Mix, Elixir or BEAM. These bundles have their own native
launcher; they do not provide ERTS daemon, RPC or hot-upgrade commands.

With the development Mix archive installed, opt a project into native routing
for ordinary `mix run`, `mix test` and `mix release`:

```elixir
def project do
  Tonic.native(app: :my_app, version: "0.1.0")
end
```

`Tonic.native/1` configures the native compiler and task aliases. Projects that
keep their ordinary Mix configuration continue to build and run on the BEAM.

To make `mix compile` build the native executable, opt into the archive compiler:

```elixir
def project do
  [
    app: :my_app,
    version: "0.1.0",
    compilers: [:tonic],
    prune_code_paths: false,
    consolidate_protocols: false
  ]
end
```

`prune_code_paths: false` keeps the installed archive's compiler task available.
Set `consolidate_protocols: false` to disable Mix’s separate BEAM protocol
consolidation. The Tonic compiler rebuilds on each invocation so evaluated
configuration and toolchain changes cannot leave a stale native artifact.
It produces a native artifact; it does not produce application
BEAM files for `mix run` or `mix release`. Use `mix tonic run`, or the
`Tonic.native/1` adapter above, to route execution to the native artifact.

The locked example in `examples/packages/` uses Decimal from Hex:

```sh
cd examples/packages
mix deps.get
mix tonic run -- 1.25 2.50
# 3.75
mix tonic build
./_build/dev/tonic/packages 10.5 2.25
# 12.75
```

Fetching a package does not establish native compatibility. Packages must use
language and runtime APIs implemented by Tonic. `rebar3` dependencies are
compiled from their Erlang sources, and C NIFs built with `elixir_make` are
compiled from `c_src/` and linked into the executable (see the
[compatibility report](https://github.com/wess/tonic/blob/main/docs/compatibility.md)). Other custom compilers,
prebuilt native libraries and other build managers fail explicitly. Umbrella
roots compile their child applications together. Yecc/leex generators run in
scratch directories; custom Mix source generators require explicit
`tonic: [generators: [:task]]` configuration.

`examples/helloweb` is a Plug, Bandit and Ecto (SQLite) service that builds to
a single native executable.

## Architecture

```
 .ex/.exs ──► lexer ──► parser ──► collect ──► expand ──► codegen ──► clang ──► native
              (tokens)   (AST)    (modules,    (Core IR:   (LLVM IR)    │
                                  protocols,   patterns,               ▼
                                  structs)     closures)          libtonic_rt.a
```

* **compiler/** (Rust) — Elixir lexer and Pratt parser (no-paren calls,
  do-blocks, stab clauses, sigils, heredocs, interpolation), module collection
  (aliases, imports, attributes, `defstruct`, `defexception`, `defprotocol`,
  `defimpl`, `defguard`, `defdelegate`, `use`, and `defmacro`),
  expansion into a small Core IR, and LLVM IR generation. The standard library
  in `lib/` is compiled together with the program (whole-program, with
  reachability pruning). The bundled library is compiled to a cached object;
  user definitions and protocol dispatch are generated for each program.
  Protocols are consolidated for `.ex` programs, while `.exs` programs retain
  script-style protocol metadata.

* **runtime/** (Rust, static library) — term representation, the garbage
  collector, bignums, persistent maps, binaries/strings/unicode, regexes, the
  process scheduler and all native built-in functions (`:erlang`, `:maps`,
  `:lists`, `:binary`, …).

* **lib/** (Elixir) — `Kernel`, `Enum`, `Stream`, `List`, `Map`, `MapSet`,
  `Keyword`, `String`, `Integer`, `Float`, `Range`, `Access`, `Inspect`
  (a port of Elixir's `Inspect.Algebra`), `String.Chars`, `Enumerable`,
  `Collectable`, `Process`, `GenServer`, `Agent`, `Task`, `Supervisor`,
  `DynamicSupervisor`, `Regex`, `File`, `Path`, `System`, `IO`, exceptions …

### Values

64-bit tagged words: 63-bit small integers, atoms, pids and `[]` are
immediates; everything else is a pointer to a boxed heap object (tuple, cons,
float, bignum, binary, sub-binary, map, closure, reference). Integers overflow
transparently into bignums. Maps use sorted flat storage for up to 32 keys and
a persistent hash array mapped trie for larger maps. Atom ordering emulates an
Elixir 1.18 / OTP 27 boot table; it does not guarantee the same iteration order
as every running BEAM VM. Sort entries when order matters.

### Garbage collection

Each process owns a private heap collected by a **precise, generational,
copying collector**. Compiled code keeps every live value in a *shadow-stack
frame* (`[prev, n, function_info, line, slot…]` allocated in the native frame
and linked from the process context), so the collector knows every root exactly and can move
objects. Immediates may live in registers since they never move. Because heaps
are per process and messages are copied on send (like the BEAM), collection
never stops other processes.

As on the BEAM, a heap has two generations. New objects are bump-allocated
(inline, without a runtime call) in a small young heap that starts at 233
words. A *minor* collection copies only the young heap: objects that survive a
second time move to the old heap, the rest stay young. A *major* collection
copies everything into a fresh old heap, and runs only when the old heap has
no room for the next promotions. Long-lived data, such as a server's state, is
therefore not copied again on every collection. Minor collections never scan
the old heap: terms are immutable, so an older object cannot point to a newer
one. `TONIC_GC_VERIFY=1` checks that invariant after every minor collection.

Executables carry only the standard library code a program can reach. The
analysis follows static calls and the shapes dynamic calls take (`mod.fun(...)`
with an unknown module, `apply/3` and `spawn/3` arguments, callback tuples such
as `{Mod, :fun, args}`, protocol dispatch); atoms in user code keep their
module's public functions. Programs that evaluate code at run time
(`Code.eval_string/2` and friends) keep everything. A hello world is about
15 MB on Apple Silicon in the current checkout. Conservative retention for
runtime-named I/O callbacks currently keeps all public function bodies;
the published beta.3 build was about 4.5 MB.

### Processes on tokio

Every Elixir process is a stackful coroutine driven by a **tokio task** on the
multi-threaded runtime. When a process has to wait — `receive` on an empty
mailbox, reduction budget exhausted, `after` timeout — it suspends back into
its task, which `.await`s the matching tokio primitive (`Notify` for mail,
`sleep_until` for timeouts, `yield_now` for fairness). Processes therefore run
in parallel across cores with preemptive-feeling fairness, and `GenServer`,
`Agent`, `Task` and `Supervisor` (written in Elixir on top of
`spawn`/`send`/`receive`/links/monitors) get all of that for free.
`TONIC_SCHEDULERS` sets the number of worker threads.

### Runtime settings

Native programs read these environment variables at startup:

| Variable | Default | Effect |
| --- | --- | --- |
| `TONIC_SCHEDULERS` | CPU count | Scheduler threads running processes |
| `TONIC_PROC_STACK_MB` | 256 | First stack of each spawned process, and the size of each further stack segment |
| `TONIC_MAIN_STACK_MB` | 1024 | First stack of the main process |
| `TONIC_MIN_HEAP` | 233 | Initial heap of each process, in words |
| `TONIC_GC_STRESS` | off | Collect on every allocation, alternating minor and major collections (testing only) |
| `TONIC_GC_VERIFY` | off | Check the generational invariant after every minor collection (testing only) |

`TONIC_KEEP_ALL=1` at compile time keeps every public standard library
function in the executable. Calls with runtime-created module/function names
already retain matching public targets conservatively, including dynamic
apply, function captures and process entry points. This setting is an explicit
request to disable public-function pruning.

Process stacks are reserved address space; memory is only committed as a
process uses it. Stacks grow like the BEAM's: a function entered near the end
of its stack continues on a new segment, so deep non-tail recursion (such as
`Enum.map/2` over millions of elements) is bounded by memory rather than by
the first stack. Frames never move. A segment's memory is released when the
process exits; a process keeps up to two spare segments for reuse.
Output to a pipe or file is batched and flushed within a few milliseconds, and
`SIGTERM`, `SIGINT` and `SIGHUP` flush pending output before the program exits.
`tonic run` passes termination signals on to the program it runs (and, on
Linux, takes the program down with it even if tonic itself is killed).

### Calls, tail calls and exceptions

Functions use LLVM's `tailcc` convention and every call in tail position is a
guaranteed tail call, so recursive loops run in constant stack. Exceptions are
values: a raising function stores `{kind, reason}` in the process context and
returns 0; callers branch to the innermost `try` handler or return 0 themselves
(no unwinding tables, no setjmp).

## What's supported

Most of the everyday language: modules, multi-clause functions with guards and
default arguments, pattern matching everywhere (including binaries and map/struct
patterns, pins), `case`/`cond`/`if`/`unless`/`with`/`for` (generators, filters,
`into:`, `reduce:`, `uniq:`, bitstring generators), `try`/`rescue`/`catch`/
`else`/`after`, `receive`/`after`, anonymous functions and captures, pipes,
structs, protocols with `@fallback_to_any` and `@derive`, exceptions,
comprehensions, sigils (`~s ~S ~c ~w ~r`), binaries and bitstrings with
bit-sized segments, processes, links, monitors, registered names, timers, ETS,
and the OTP-style abstractions above. Regexes use PCRE2, including
backreferences and lookaround. Exceptions capture source-aware stack traces.

Template macros expand in the compiler. Macros that compute their expansion
run in a cached native macro host using `Tonic.Eval`; no external Elixir or
BEAM runtime is required to run a script or expand its macros.

User modules support `defoverridable` and calls to the previous implementation
with `super(...)`, including defaults and successive overrides. Compilation
hooks support `@on_definition` and `@before_compile` for inspecting definitions,
updating attributes, and injecting code. `@after_compile` runs after LLVM IR is
generated; its second argument contains the program's LLVM IR as a binary,
rather than BEAM bytecode. Interpreted modules created through `Code.eval_*`
have no emitted artifact and pass an empty binary. Compile-time output is
forwarded to stderr so it cannot corrupt the macro-host protocol or script
stdout.

`tonic check` parses and expands without generating LLVM IR, so it runs
definition and before-compilation hooks but does not run after-compilation hooks.

### Limitations

* Compile-time execution uses Tonic's evaluator and bundled library, so it is
  limited to the language and APIs implemented here. It is not a BEAM VM.
* No BEAM hot code loading, distributed nodes or port drivers; TLS is rustls
  (TLS 1.2 and 1.3, no DTLS). NIFs must be C sources compiled into the
  executable, using the implemented `erl_nif` subset. Process and system
  introspection cover a subset of Erlang's APIs.
* Mix project loading requires installed Mix. Native compilation supports
  fetched sources, not arbitrary BEAM dependencies or custom package build tasks.
* Map iteration order and anonymous-function identifiers can differ from
  reference Elixir. Neither is a portable ordering or identity contract.
* PCRE2 and OTP 27's PCRE engine can differ in accepted patterns, compile-error
  wording, and offsets. Common parenthesis and quantifier errors use OTP 27
  wording; this does not imply complete regex-engine equivalence.

# Compatibility

Tonic 0.1.1-beta.1 development source compiles supported Elixir and Erlang source to LLVM and links a native runtime. `.exs` scripts use the same compiler. Native executables do not contain BEAM bytecode.

This report follows the current development source. The API inventory, Req
coverage, managed native-resource lifetimes, expanded socket semantics, and
native Mix test/release workflows below are changes after the published
0.1.0-beta.3 bundles. Build the current checkout to exercise them.

The [API conformance inventory](https://github.com/wess/tonic/blob/main/docs/coverage.md) compares reference exports with
native declarations and reviewed test evidence. A declaration alone defaults
to partial support; counts do not measure a percentage of Elixir compatibility.

## Macros and compilation callbacks

User macros can execute compile-time code through the macro host. Coverage includes caller environments, computed expansions, default macro arguments, map splicing, generated definitions, `use`, and chained overridable functions and macros. In a Mix project, compile-time code can call `Mix.Project.config/0` (the `:app` and `:version` of the project the code belongs to) and the functions of each project's own `mix.exs` module.

`@on_definition` callbacks receive definition metadata and can update attributes seen by subsequent definitions. `@before_compile` callbacks can inject definitions and attributes. Native `@after_compile` callbacks run after LLVM generation; their second argument is the emitted LLVM IR binary. It is not a BEAM module binary. Interpreted `Code.eval_*` modules receive an empty binary because they do not emit a compiled artifact.

Modules created through `Code.eval_string` run in Tonic's interpreter. Compiled
code can call their ordinary public functions through remote calls, `apply` and
external captures; private functions stay private. Function and macro reflection
recognize those definitions. `compiler/tests/evaluation.rs` compares these paths,
exceptions and moving-GC behavior with BEAM. This does not implement BEAM artifact
loading, full generated-module introspection, or native module replacement.

## Concurrent applications

The supervised load test runs four producers against a GenServer, checks every result, monitors producer exits, kills the worker, and verifies that its supervisor starts a new worker. Requests retain closures, maps, lists, strings and tuples while moving garbage collection is forced on every allocation.

The ordinary test runs for five seconds per engine. The release gate extends each engine to sixty seconds. A cycle includes sixty validated requests and one automatic worker restart; the test prints completed request and restart counts. No throughput or memory ceiling is implied by this check.

```sh
cargo test -p tonic --test soak -- --nocapture
TONIC_SOAK_SECONDS=60 cargo test -p tonic --test soak -- --nocapture
```

## Supported project boundaries

Mix evaluates project metadata, dependency selection and compile configuration. Coverage includes computed metadata, transitive path dependencies, `only`, `targets`, `runtime: false`, application startup ordering, version checks, lock checks, and runtime configuration that reads the executable's environment.

Tonic accepts the supported standard Mix source compilation pipeline, including umbrella roots and interdependent child applications. `rebar3` dependencies are compiled from their Erlang sources and `.app.src` specification; yecc/leex generation runs in a scratch directory. Mix source generators explicitly listed in `tonic: [generators: [:task]]` run through installed Mix before native source collection. Their host dependencies must be available. Dependency Mix tasks are not linked into the native program. Undeclared custom compiler tasks, prebuilt BEAM/object-only artifacts, prebuilt native shared libraries and other build managers are rejected with diagnostics. Fetch dependencies with `mix deps.get` or `mix tonic.build --deps-get`; native compilation does not fetch missing packages.

`tonic test`, `mix tonic test` and `mix tonic.test` compile and execute ExUnit
natively, including helpers, application startup, file/directory/file:line
selection, tag filters, seed, timeout, trace and failure-limit options.
`mix tonic release` creates a relocatable native executable with application
`priv` assets and runtime configuration. `Tonic.native/1` is an opt-in project
adapter for ordinary `mix run`, `mix test` and `mix release`; projects that do
not opt in keep their normal BEAM pipeline. Native releases do not implement
ERTS release daemon, RPC or hot-upgrade protocols. These workflows are exercised
in `compiler/tests/tooling.rs` and `compiler/tests/tooling/filtering.rs`.

## NIFs

Dependencies built with `elixir_make` whose `c_src/` contains a C NIF (`ERL_NIF_INIT`) are compiled from source against Tonic's `erl_nif.h` and linked into the executable. The `-D` options of the dependency's Makefile `CFLAGS` are applied; compiled objects are cached. A module's `@on_load` callback runs at startup, `:erlang.load_nif/2` binds the linked library, and functions whose body is `:erlang.nif_error/1` call into it.

Tonic implements a subset of the `erl_nif` API: terms, binaries, resources, environments, messages, mutexes and monotonic time. NIF calls run on the calling process's scheduler thread. Managed resource references retain native state across GC, process messages, ETS, serialization roundtrips and NIF environments; the final release invokes the native destructor. Explicit `enif_keep_resource`/`enif_release_resource` ownership is preserved independently of term lifetimes. `runtime/tests/resources.rs` and `compiler/tests/resources.rs` exercise reclamation and copies. Rust NIFs (Rustler), prebuilt `.so`/`.dylib` files and dirty-scheduler semantics are not supported.

## Networking

`:gen_tcp` provides TCP listen, accept, connect, send, recv, close, shutdown and controlling process, in passive, `active: :once`, `active: true` and `active: N` modes. List delivery is the default; binary/header delivery and raw, 1/2/4-byte length-prefixed and line packets are supported. Socket options include local address/family binding, keepalive, nodelay, receive/send buffers and send timeouts; unsupported options return errors. `:inet` covers `setopts`, `getopts`, `sockname`, `peername`, `getstat`, `port`, address parsing and formatting. Waiting socket operations run on the runtime's I/O driver and do not block scheduler threads. `:erlang.decode_packet/3` additionally handles HTTP packet decoding.

`:gen_udp` provides `open/1,2`, `send/3,4` (address tuples or host names), `recv/2,3`, `close/1` and `controlling_process/2`, in passive, `active: :once`, `active: true` and `active: N` modes with `{:udp, socket, ip, port, data}` and `{:udp_passive, socket}` messages, `:list` or `:binary` delivery, and `:inet`/`:inet6`, `:ip`, `:reuseaddr`, `:reuseport`, `:broadcast`, `:recbuf` and `:sndbuf` options. `:inet.setopts/2`, `getopts/2`, `sockname/1`, `port/1`, `getstat/1` and `close/1` accept UDP sockets.

`:ssl` provides TLS 1.2 and 1.3 clients and servers on rustls (with the ring provider; no OpenSSL): `connect/2,3,4` to a host or over a connected `:gen_tcp` socket, `listen/2`, `transport_accept/1,2`, `handshake/1,2,3`, `send/2`, `recv/2,3`, `close/1,2`, `shutdown/2`, `setopts/2`, `getopts/2`, `controlling_process/2`, `peername/1`, `sockname/1`, `getstat/1,2`, `peercert/1`, `negotiated_protocol/1` and `connection_information/1,2`, in passive, `active: :once`, `active: true` and `active: N` modes with `{:ssl, socket, data}`, `{:ssl_closed, socket}`, `{:ssl_error, socket, reason}` and `{:ssl_passive, socket}`, `:list` or `:binary` delivery and `{:packet, :raw | 0 | 1 | 2 | 4 | :line}` framing. Options: `verify` (`:verify_peer` is the client default, and without `cacerts`/`cacertfile` it fails with OTP's `{:options, :incompatible, ...}` error), `cacerts` (DER or `:public_key.cacerts_get/0` records), `cacertfile`, `cert`/`key`, `certfile`/`keyfile`, `certs_keys`, `server_name_indication`, `versions`, `alpn_advertised_protocols`, `alpn_preferred_protocols`, `fail_if_no_peer_cert`, `sni_hosts`, `customize_hostname_check`, `:inet6` and `:ip`. Handshake failures return OTP's `{:tls_alert, {alert, description}}` reasons (`:unknown_ca`, `:handshake_failure` for a host name mismatch, `:certificate_required`, `:no_application_protocol`, ...), and sockets close when their controlling process exits. `:ssl.start/0,1`, `:ssl.stop/0`, `Application.ensure_all_started(:ssl)`, `:ssl.versions/0`, `:ssl.cipher_suites/1,2,3` and `:ssl.filter_cipher_suites/2` answer as OTP 27.3 does for the suites rustls implements. `:public_key` provides `cacerts_get/0`, `cacerts_load/0,1`, `pem_decode/1`, `pem_encode/1`, `pem_entry_decode/1`, `der_decode/2` for certificates and RSA/EC keys, `pkix_decode_cert/2` (`:plain` and `:otp`) and `pkix_verify_hostname_match_fun/1`. Programs that never call `:ssl` or `:public_key` link none of the TLS code.

## Ports

`Port.open/2` and `:erlang.open_port/2` start external programs with `{:spawn, command}` (run as `/bin/sh -c "exec command"`, as OTP does) and `{:spawn_executable, path}`. Supported options are `:binary`, `:exit_status`, `:eof`, `{:args, list}`, `{:arg0, name}`, `{:cd, dir}`, `{:env, list}`, `:stderr_to_stdout`, `:use_stdio`, `:nouse_stdio` (the program uses fds 3 and 4), `{:line, n}`, `{:packet, 1 | 2 | 4}`, `:stream`, `:in`, `:out`, `:hide` and `{:parallelism, bool}`. The owner receives `{port, {:data, data}}` (`{:eol, line}` and `{:noeol, part}` in line mode), `{port, {:exit_status, status}}`, `{port, :eof}`, `{port, :closed}` and `{port, :connected}` in OTP's order. `Port.command/2,3`, `send(port, {pid, {:command | :connect, _}})`, `send(port, {pid, :close})`, `Port.close/1`, `Port.connect/2`, `Port.info/1,2`, `Port.list/0`, `Port.monitor/1`, links, `exit(port, reason)` and `badsig` exit signals follow OTP 27; a port closes with its connected process. Ports are their own term type: `is_port/1`, printing as `#Port<0.N>` and term order match the BEAM, and ports survive `term_to_binary/1` round trips. Program output is read on the runtime's I/O driver and never blocks a scheduler thread. `System.cmd/3`, `System.shell/2` and `:os.cmd/1,2` are Elixir's and OTP's own implementations over ports.

`Port.list/0` omits the BEAM's own stdio ports (`#Port<0.0>` and `#Port<0.1>`), `{:spawn_driver, _}` and `{:fd, _, _}` are not supported, and `Port.info/2` reports an approximate `:memory` and a `:id` equal to the port number. `spawn_executable` of a directory fails with `:eacces` instead of opening a port that exits at once.

Distributed BEAM nodes, BEAM bytecode loading and full compatibility with undocumented OTP internals are outside this release's supported surface. Passing the source and runtime tests does not establish those capabilities.

## Known differences

These differ from Elixir 1.18 / OTP 27 in this release. Each is either intentional or tracked in TODO.md.

- Redefining a module (a second `defmodule` with the same name) is a compile error; Elixir replaces the module at run time.
- `:erlang.phash/2` and `:erlang.phash2/1,2` match OTP 27 for every term except pids, references and anonymous or local funs. Pids and references hash their printed numbers, which differ from the BEAM's; anonymous funs cannot reproduce OTP's per-module code checksum. External funs (`&Mod.fun/arity`) match.
- `Macro.expand/2` and `Macro.expand_once/2` expand aliases, user macros (remote, and imported ones when given `__ENV__`), public `defguard` macros including defaults, and the Kernel macros `if`, `unless`, `&&`, `||`, `!`, `|>`, `is_nil`, `then`, `tap`, `to_string`, `to_charlist` and `match?`. Other Kernel macros can remain unexpanded.
- `:calendar.local_time_to_universal_time/1` applies the current UTC offset rather than the offset in effect at the given local time, so results differ across a daylight saving change.
- Elixir's unused variable, ungrouped clause and duplicate map key warnings are emitted for code you write, but not inside code a dependency's macro generates (for example the body of a `Plug.Router` route). Elixir's other warnings (deprecations, type checking, unused functions, aliases and imports) are not emitted, and some invalid programs Elixir rejects are still accepted.
- Stack trace frames for anonymous functions inside `with ... else` and other inlined code are named after the enclosing function, where the BEAM names a generated function such as `-w/1-fun-0-`.
- A `quote` of a sigil omits the `delimiter:` metadata.
- `quote bind_quoted:` supports literal keyword lists and lexical `Kernel.binding`; custom macros or attributes producing that option are not fully expanded before validation and can be rejected.
- `:zlib` state is reclaimed when its last term owner disappears, including streams never explicitly closed. Closing a stream twice still raises `:badarg` rather than `:not_initialized`. Compressed bytes come from stock zlib 1.3.2; OTP builds linked to another zlib can produce different bytes while remaining mutually decompressible.
- Sockets are references rather than ports, so they print as `#Reference<...>` and `is_port/1` is false for them.
- `:gen_udp.connect/2,3`, connected `send/2`, multicast membership, TTL/TOS/dontroute and socket option readback are implemented. Ancillary-data receive APIs remain unsupported; unsupported options return an error instead of being ignored.
- TLS runs on rustls: TLS 1.2 and 1.3 only, no DTLS, renegotiation or session resumption across independently created connections. Cipher selection/order, verification depth, local binding and socket settings are applied. Client/server `verify_fun`, `partial_chain`, custom hostname `match_fun` and dynamic `sni_fun` callbacks execute through a cancellable process bridge. Rustls/webpki rejects unknown critical X.509 extensions during certificate parsing, so a callback cannot override those failures as OTP can. Unsupported options are rejected. Nested TLS (`:cb_info`) remains unsupported.
- TLS alert descriptions say `In state handshake` where OTP names its state machine state and source line, and OTP's notice-level log line for each alert is not printed. Local errors map to the alert OTP sends for unknown CAs, host name mismatches (`:handshake_failure`), expired certificates, missing client certificates and ALPN mismatches, and to the closest alert otherwise; the alert a rustls peer sends can differ from OTP's (a tonic client rejecting a host name sends `:bad_certificate` where OTP sends `:handshake_failure`). `connection_information/1` returns `protocol`, `selected_cipher_suite`, `session_resumption`, `sni_hostname` and `versions` only, not the session or option keys.
- TLS sockets are `{:sslsocket, reference, :tls}` tuples rather than OTP's records holding a port and pids. `:ssl.getstat/1,2` counts decrypted application data with the four `recv_`/`send_` `oct` and `cnt` keys, where OTP reports the TCP socket's statistics. `:ssl` works without starting the `:ssl` application, where OTP exits.
- `:public_key.cacerts_get/0` reads the system's PEM bundle (`SSL_CERT_FILE`, then /etc/ssl/cert.pem, /etc/ssl/certs/ca-certificates.crt and the other usual paths); OTP on macOS reads the keychains instead. Decoded certificates in the `:otp` form keep extension values as DER, and `:public_key` has no signing, verification, encryption or DER encoding.
- `:re` with `[:unicode]` but without `:ucp` matches `\w` and similar classes against ASCII only; use `~r/.../u` (which sets `:ucp`) for Unicode word characters.
- Converting a very large integer to a float rounds correctly (IEEE 754); the BEAM can differ in the last digit.
- `Code.string_to_quoted/1` error locations report line 0 without a column, and a compiled regex's `re_pattern` is not a real PCRE binary.
- Small maps with atom keys print keys in source order rather than atom-table order.
- Memory: each blocked process holds at least one page of its stack, so a process costs about 20 KB on Apple Silicon (16 KB pages) and about 7 KB on Linux (4 KB pages), compared to about 3 KB on the BEAM. Deep non-tail recursion works to any depth memory allows, but a stack frame takes about four times the memory of a BEAM frame (10 million frames of `n + f(n - 1)` use about 2 GB, the BEAM about 0.6 GB).
- Tree shaking conservatively retains matching public targets when an apply, capture, spawn or dynamic call cannot determine its module/function names statically. Runtime-created names do not require `TONIC_KEEP_ALL=1`; that variable remains an explicit request to retain every public function. The standard I/O server accepts runtime-named callbacks, so current analysis retains all public bodies even for hello world (~15 MB on Apple Silicon, versus ~4.5 MB in beta.3). Export metadata is retained independently of code pointers, and private functions remain inaccessible through reflection and dynamic calls.
- A project configured only with `compilers: [:tonic]` still produces no BEAM files for ordinary Mix tasks. Use the `Tonic.native/1` adapter for native run/test/release workflows, or keep the default compilers to run on the BEAM.
- Output written by a module body (`IO.puts` inside `defmodule`) appears on stderr while the program compiles, not when it runs.
- Compile-time process state belongs to the macro host. A process dictionary entry written during compilation does not become an entry in the native executable's runtime process, unlike compilation and execution within one BEAM script process.
- Logger's `debug`/`info`/... and `log` are functions, so calling them without `require Logger` works where Elixir raises.
- Tuple keyword misuse, invalid `as:` aliases, guard/function kind conflicts, private guard access, repeated `defoverridable` and undefined `@spec` targets now have focused rejection tests. Complete equivalence with every Elixir diagnostic and warning is not established.
- Stack traces keep a frame for a function that tail-calls a function the BEAM inlines (such as `String.to_atom/1`), show each frame of repeated body recursion, and add an `erlang.erl` `apply/2` frame to Task crash reports.
- Sorting terms that compare equal but differ (`1` and `1.0`) can order them differently from `:lists.sort/1`.
- A few error messages are worded differently: binary construction (`"a" <> 1`), updating a missing map key, `:erlang.binary_to_atom/2` on invalid UTF-8, `Process.exit/2` with a non-pid, and `Base.decode64!/1` on bad padding.
- `:inet.getifaddrs/0` is not implemented.
- Quoted `bind_quoted` variables retain source line/column metadata and explicit `var!` bindings participate in unused-variable warnings. Broader macro/AST metadata equivalence still needs conformance coverage.

# Tonic TODO

The development version is 0.1.1-beta.1; the latest public beta is 0.1.0-beta.3.
Tonic targets scripts and applications within
the supported boundary in docs/compatibility.md. The next priority is broader
Elixir source and runtime compatibility, backed by comparisons against
Elixir/OTP. Supporting `.ex` and `.exs` files does not establish full BEAM
compatibility.

- [x] 0.1.0-beta.1 (2026-10-16): first public release.

  and stricter compile errors, OTP-exact phash2/URI/RFC 3339.
- [x] 0.1.0-beta.2: generational collector, tree-shaken executables, smaller
  process footprint.

## Beta follow-ups

Development source after beta.3 adds these portability checks and fixes:

- [x] Generate an API inventory against pinned Elixir/OTP exports, with reviewed
  classifications, linked regressions and stale-output checks in CI.
- [x] Retain dynamically named apply/capture/spawn targets conservatively.
- [x] Embed remote captures from interpreted compile-time modules in module
  attributes; compare unchanged Req GET/POST/redirect/status behavior with BEAM.
- [x] Reclaim atomics/counters, unclosed zlib state and NIF resources when their
  final term/native owner disappears, including messages, ETS and ETF recovery.

- [x] Run ExUnit natively and produce relocatable native application bundles;
  opt-in Mix aliases preserve ordinary run/test/release command workflows.

Known differences are listed in docs/compatibility.md. In priority order:

- [x] Grow process stacks on demand: functions continue on a new stack segment
  near the end of the current one.
- [ ] Smaller stack frames: a frame of `n + f(n - 1)` takes ~210 bytes, about
  four times the BEAM's.
- [x] Generational collection: long-lived data is no longer copied on every
  collection, and heap growth copies once.
- [ ] Per-process baseline: a blocked process holds a stack page (16 KB on
  Apple Silicon). Copying small stacks out on block would approach the BEAM's
  ~3 KB.
- [ ] Executable size: hello world is now ~15 MB on Apple Silicon because
  runtime-named I/O callbacks conservatively retain all public functions.
  Specialize I/O request reachability without breaking dynamic apply; also
  make regex and exception formatting reachable only when used.
- [ ] Make `:calendar.local_time_to_universal_time/1` use the offset in effect
  at that local time, as the BEAM does.
- [ ] Emit Elixir's remaining compile warnings (unused functions, aliases and
